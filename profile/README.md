<p>第一次把 Claude API 接到住宅出口上，报错往往一个接一个：先是连不上，改完代理又变成 401，鉴权过了开始撞 429，并发压上去又遇到读超时。这些不是五个独立的问题，而是一条链上的五个关口。这篇按实际踩坑顺序串一遍，每个关口给出现场特征、首查位置和可落地的参数，顺手把重试策略该写在哪儿说清楚。全程只讲客户端能控制的部分。</p>

<h2>一、第一关：请求根本没出去</h2>
<p>现场特征很统一：连接超时、DNS 解析失败，或者返回一个不属于 API 的错误页。这说明流量没走到代理，或者走到了但出口不通。</p>
<h3>先确认代理本身是通的</h3>
<p>命令行验证是最快的一步：<code>curl -x http://用户:密码@地址:端口 -sS https://api.ipify.org</code>。能拿到地址，说明代理链路可用；拿不到就先解决链路，别急着改代码。</p>
<p><strong>再看客户端有没有真的用上代理。</strong>Python 的 requests 会读 <code>HTTPS_PROXY</code> 与 <code>HTTP_PROXY</code>，但不少 SDK 只读显式传入的参数。稳妥做法是代码里显式指定 proxies，环境变量只作为兜底。同时把内网地址写进 <code>NO_PROXY</code>，避免内部请求也被绕出去。</p>
<h3>DNS 是第二个坑</h3>
<p>走 HTTP 代理时域名由代理解析，走 SOCKS5 时可能由本地解析，两种行为不同。若本地 DNS 污染，表现为间歇性解析失败。判断方法：<code>curl -x socks5h://...</code> 里的 h 表示交给代理解析，加上它再试一次，症状消失就说明是本地解析的问题。</p>

<h2>二、第二关：出去了，但鉴权不过</h2>
<img src="/tp.png" alt="Claude API 经住宅出口调用时的鉴权并发与重试链路">
<p>401 和 403 长得很像，处理方式完全不同，先分清再动手。</p>
<h3>401 先查请求头</h3>
<p>Claude API 用 <code>x-api-key</code> 头传密钥，不是 Bearer。常见错误是把密钥塞进 Authorization，或者用了别家的写法。另外 <code>anthropic-version</code> 是必填头，缺失时也可能返回参数类错误，看起来不像鉴权问题。</p>
<h3>403 更像环境问题</h3>
<p>密钥正确但被拒，通常与账号状态、地区限制或额度有关。这时候换密钥没用，先看账号后台的用量与状态页。出口地区与账号注册地区不一致时，也可能出现类似表现，排查时把出口国家一起记下来。</p>

<p><strong>把错误体打出来。</strong>响应体里通常有 error.type 与 message，直接打印比猜快得多。调试阶段把状态码、错误类型、请求 ID 一起写进日志，后面查问题能省很多时间。</p>

<h2>三、第三关：并发一高就开始排队</h2>
<p>单条请求跑通，压到十条就变慢，压到三十条开始大量 429。这一关要区分是客户端排队，还是服务端限流。</p>
<h3>先分清两种「慢」</h3>
<p>客户端排队表现为请求发出前的等待时间变长，服务端限流表现为请求发出后很快返回 429。抓一下每个请求的耗时分布，两种情况的图形完全不同。</p>
<h3>并发要控在多少</h3>
<p>没有通用数字，取决于账号等级与套餐。稳妥做法是设一个信号量，从低并发起，每次加五，观察 429 比例，超过一定比例就停在上一档。这个上限写进配置文件，别硬编码在业务里。</p>
<p><strong>连接池别开太大。</strong>连接池大小与并发数不匹配时，会出现连接复用率低、握手次数多的情况，出口侧看起来像是频繁新建连接。把池大小设成与并发数接近，复用率会明显改善。</p>

<h2>四、第四关：长响应被读超时打断</h2>
<p>流式输出最容易在这里翻车：前几秒正常，十几秒后连接被切断，客户端报读超时。</p>
<h3>三个超时要分开设</h3>
<p>连接超时（建议十秒上下）、读超时（流式场景要放宽到几分钟）、总超时（按最长响应估）。三者混成一个值，是流式请求失败的主要原因。</p>
<h3>流式要有心跳判断</h3>
<p>长时间没有数据块到达时，先判断是模型在思考还是链路断了。做法是记录最后一个数据块的时间戳，超过阈值再断开重连；不要一没有输出就立刻重试，容易把一次慢响应放大成多次请求。</p>
<p><strong>中断续接的成本。</strong>重新发起意味着重新计费。对长文档生成类任务，宁愿把读超时放宽，也不要频繁重来。把 max_tokens 设成合理值，能减少无谓的长响应。</p>

<h2>五、第五关：重试怎么写才不放大故障</h2>
<p>重试是最容易帮倒忙的一环。写错了，一个上游抖动会变成雪崩。</p>
<h3>只重试该重试的</h3>
<p>429、5xx、连接类错误可以重试；400、401、403、404 这类重试没有意义，只会浪费额度。按状态码分支，而不是统一重试三次。</p>
<h3>退避要带抖动</h3>
<p>指数退避加上随机抖动，避免所有客户端在同一时刻齐步重试。若响应头里有 retry-after，优先按它来，别自作聪明。重试次数建议三次封顶，超过就把错误抛给上层。</p>
<h3>幂等性怎么保证</h3>
<p>纯生成类请求本身不幂等，重复调用会产生两份结果两份计费。做法是在业务层加请求去重键，把结果落库后再返回；重试只针对「没有拿到完整响应」的情况。</p>
<p><strong>把可观测性补上。</strong>至少记录四项：出口编号、状态码、总耗时、重试次数。四项按出口维度聚合，能很快看出某条线路是不是在拖后腿，比逐条 ping 有效。</p>

<h2>常见问答</h2>
<h3>接了住宅代理后延迟明显变高，正常吗？</h3>
<p>答：常见。住宅出口通常离你较远，跨洲链路增加一百到三百毫秒属正常范围。若延迟高于这个区间且伴随丢包，先用 mtr 看丢包集中在哪一跳，再判断是本地、中转还是出口的问题。</p>
<h3>429 一直出现，是线路的问题吗？</h3>
<p>答：多数不是。429 表示触发限流，与账号等级、并发设置、请求频率关系更大。先降并发、加退避，再看是否缓解；换线路通常解决不了限流。</p>
<h3>流式响应总在中途断，怎么排查？</h3>
<p>答：先看读超时设置是否过短，再看中间是否有代理或网关的空闲超时。逐层用 curl 直连测试，能定位到具体哪一跳在断开。定位前不要盲目加重试。</p>
<h3>住宅出口需要为 API 单独一条吗？</h3>
<p>答：看调用量。低频调用可以与日常浏览共用一条；高频、长连接、需要稳定延迟的场景，单独一条更便于观测和限流。共用的代价是出问题时不好判断是谁影响了谁。</p>
